## Plan / spec used

The human operator pasted the official challenge PDF plus a personal
"project orchestration" document proposing the tech stack (Laravel + React
Starter Kit, Inertia, TypeScript, Tailwind, Fake Store API, Laravel Mail,
SQLite, Pest) and, separately, a git branching ceremony (an `integration`
branch with a dedicated feature branch + PR per feature). Claude Code ran a
plan-mode workflow: it verified the target directory was actually empty
(contradicting an earlier, incorrect memory of a finished implementation),
then used a Plan subagent to turn the tech-stack decisions and the
challenge's acceptance criteria into a concrete architecture (the
`ProductProvider` contract, the featured-product selection rule, the test
plan) before writing any code. That synthesized plan is what was actually
followed; it is not committed as a separate file in this repo.

## Key prompts / moments that shaped the solution

1. **Branch workflow conflict.** The orchestration doc asked for a full
   `integration`-branch ceremony with a separate PR per feature (8+ PRs).
   The operator was asked directly whether to follow that literally or to
   match the challenge brief's own "single PR, 2-3 hour time-box" framing,
   and chose the latter. The doc's per-feature _content_ (edge cases like
   timeout handling, duplicate-submission guards, rating tie-breakers) was
   still folded into the single-branch implementation; only the branch/PR
   ceremony was dropped.
2. **Scoping the swappability requirement.** Asked to design "the minimum
   set of interfaces that satisfies 'the data source and email provider are
   expected to change,'" the plan explicitly rejected a hand-rolled
   `EnquiryNotifier` interface around Laravel's `Mail` facade (ceremony with
   no behavioral difference) and a `ProductProvider` with one method per
   Fake Store endpoint (unneeded surface for a 20-item catalogue). This kept
   the domain layer to two files.
3. **"Top rated" selection.** The acceptance criterion says "GIVEN I have
   chosen 5 products to be top rated," which is curation language. The
   solution treats the 5 featured ids as owner-configured (`FEATURED_PRODUCT_IDS`),
   not purely algorithmic, with a rating-based fallback — a deliberate
   reading of the brief's intent over its literal minimum.
4. **The caching bug (see below)** — diagnosing it required stepping outside
   the automated test suite (which was all green) and actually running the
   live app.

## Where AI got something wrong, and how it was caught

The most significant mistake: `FakeStoreProductProvider::all()` originally
cached hydrated `Product` DTOs (via `Cache::remember`). All 16 Pest tests
passed, PHPStan passed, the frontend built cleanly — every automated check
was green. But when the app was actually run and clicked through (via curl
against the live Herd-served site and direct `tinker` calls), the **second**
request to any page returning product data threw:

```
FakeStoreProductProvider::all(): Return value must be of type
Illuminate\Support\Collection, __PHP_Incomplete_Class returned
```

Root cause: Laravel 13 ships a security hardening default,
`cache.serializable_classes => false`, which makes the database cache
driver call `unserialize($value, ['allowed_classes' => false])` — silently
turning **every** cached object back into a `__PHP_Incomplete_Class` stub on
read, rather than throwing. The Pest suite never caught this because
`phpunit.xml` forces `CACHE_STORE=array` for tests, which never serializes
at all — so the bug only existed on the "real" cache driver, invisible to
the test suite as originally written.

This was caught by **actually running the app** (`composer run dev` /
`https://officeworks.test`) rather than trusting "tests pass, ship it," then
reading Laravel's `DatabaseStore`/`CacheManager` source to find the real
cause instead of guessing. The fix: cache the raw array payload from the
Fake Store API, not hydrated DTOs, and hydrate `Product` objects on every
read (cheap for a 20-item list). A regression test
(`tests/Feature/ProductProviderCachingTest.php`) was added that forces
`cache.default = database` and asserts a second, cache-hit call still
returns correctly-typed `Product` instances — specifically to catch this
class of bug if it recurs, since the rest of the suite can't see it.

Smaller corrections along the way: an initial PHPStan pass flagged an
unresolvable template type on a bare `collect()` call and a missing
controller return type, both one-line fixes; a stray `(cache table missing)`
`tests/Unit` directory in `phpunit.xml` referencing a deleted folder was
removed rather than recreated with a placeholder test, since no unit tests
were needed for this scope.

## Verification actually performed

`php artisan test` (17 Pest tests, all passing, zero real network calls),
`composer types:check` (PHPStan/larastan, 0 errors), `composer lint:check`
(Pint), `npm run types:check` (`tsc --noEmit`), `npm run check` (frontend
lint/format), a production `npm run build`, and manual exercising of every
route against the live, Herd-served app (curl status-code checks for all
routes including 404 cases, and `tinker`-driven calls exercising the real
Fake Store API integration). No Chrome was available in this environment,
so no actual browser/visual check or screenshot was taken — see
`DECISIONS.md` for the Playwright/E2E follow-up this implies.
